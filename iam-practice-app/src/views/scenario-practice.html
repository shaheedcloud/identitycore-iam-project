How to use scenarios

IdentityCore is local-first and skill-practice focused. These scenarios do not execute real provider workflows, call external APIs, transform tokens, create persistent learner progress, or connect to AWS, Entra ID, Okta, SCIM targets, SAML IdPs, SIEM, email, or background jobs.

Treat each scenario as an explanation drill: who is the identity, what access was requested, what decision was made, why it happened, and what safe evidence would support that answer.
Practice Scenario Authentication context scenario
Identity context: A learner signs in with local dummy login as user@identitycore.local.
Access request: Open the dashboard and review the current session source.
Decision: Allow dashboard access because the user is authenticated.
Reason: Authentication creates an IdentityCore browser session, but it does not grant privileged routes.
Evidence example: `/api/me` shows a safe local profile without password, raw tokens, tenant data, provider secrets, or external claims.
Interview prompt: Explain what proves the user is signed in.
Architecture prompt: What extra controls would production authentication require?
Open dashboard
Simulated Claims interpretation scenario
Identity context: A local user has simulated claims such as email, role, groups, department, and job title.
Access request: Interpret the claims and token-shaped object on the claims page.
Decision: Display safe local claim data for learning only.
Reason: Claims help explain identity facts, but simulated claims are not signed, validated, or trusted as production tokens.
Evidence example: `/api/claims` and `/api/token-simulation` return safe local examples that are clearly marked as not real JWTs.
Interview prompt: Which claims are identity facts and which claims may influence access?
Architecture prompt: What validation is required before trusting a real token?

Protected Role mapping access decision scenario
Identity context: A user may come from local dummy login, Entra OIDC, or Okta OIDC.
Access request: Determine the local role and whether a safe mapping rule matched.
Decision: External users map conservatively unless an explicit allowlisted rule is designed.
Reason: External claims and groups must not automatically grant admin access.
Evidence example: `/api/role-mapping` shows current provider, local role, role source, mapping outcome, and RBAC examples without raw tokens.
Interview prompt: Why is allowlisted mapping safer than trusting every external group?
Architecture prompt: Where should the final authorization decision happen?

Review Next Access denied scenario
Identity context: A standard user has an authenticated session and a non-admin local role.
Access request: Attempt to open the admin-only page.
Decision: Deny access and show the access denied experience.
Reason: Authentication succeeded, but local RBAC requires the `admin` role for `/admin`.
Evidence example: `/access-denied` shows the least-privilege lesson while protected routes continue enforcing local RBAC.
Interview prompt: Explain why a signed-in user can still be denied.
Architecture prompt: What evidence should appear in an audit trail for denied access?

Simulated Joiner, Mover, Leaver scenario
Identity context: A local lifecycle identity is onboarded, moved between responsibilities, or deactivated.
Access request: Review what changed and what evidence was produced.
Decision: Show simulated lifecycle evidence without calling HR, Entra, Okta, SCIM providers, or workflow engines.
Reason: JML practice teaches identity governance concepts while remaining local and in-memory.
Evidence example: JML readiness and evidence summaries can show joiner, mover, and leaver records without granting access by themselves.
Interview prompt: What evidence proves a leaver was deactivated?
Architecture prompt: How should lifecycle changes interact with access reviews?

Evidence Example Audit evidence scenario
Identity context: A learner triggers local login, logout, route denial, SCIM fail-closed, JML, SAML, or JWT practice activity.
Access request: Review safe troubleshooting evidence.
Decision: Display redacted in-memory evidence only.
Reason: Audit practice should help explain what happened without logging passwords, cookies, raw tokens, assertions, bearer values, secrets, or real provider data.
Evidence example: audit readiness summarizes local events and redaction rules. It is not a SIEM, CloudTrail ingestion path, or production audit log.
Interview prompt: What is useful troubleshooting evidence for an IAM incident?
Architecture prompt: Which fields must be masked before logs leave an application?

Scenario guide

Decision model

  • Identify the user and authentication source.
  • Inspect only safe claim or context indicators.
  • Determine the local role and role source.
  • Compare the request with the protected route policy.
  • Explain the allow or deny decision.
  • Point to simulated evidence that supports the decision.
This page is not a training engine, scoring engine, workflow state machine, automation runner, or progress tracker.
