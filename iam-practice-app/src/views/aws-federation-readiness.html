AWS federation readiness

Learn the AWS IAM federation model before any real AWS account, credential, role, provider, or CloudTrail source is connected to IdentityCore.

AWS federation is not IdentityCore login. IdentityCore local RBAC controls this app. AWS IAM roles and permission policies would control AWS access in a later explicit federation design.

Federation Flow

Step Future concept Phase 20 status
1 Entra ID or Okta authenticates the workforce user. Explained only. No AWS federation request is started.
2 AWS trusts a configured SAML or OIDC provider. Placeholder concepts only. No provider ARN is stored.
3 The user assumes an approved AWS IAM role. Readiness only. No role ARN or account ID is stored.
4 A permission policy limits what that role can do. Placeholder examples only. Nothing is attached in AWS.
5 CloudTrail records future AWS activity. Planning only. No CloudTrail logs are ingested.

Trust policy

Who may assume the role?

A trust policy defines the trusted identity provider and conditions for role assumption. Phase 20 uses placeholders only.

{
  "Principal": {
    "Federated": "SAML_PROVIDER_PLACEHOLDER"
  },
  "Action": "sts:AssumeRoleWithSAML"
}
Permission policy

What may the role do?

A permission policy defines allowed AWS actions after role assumption. Future lab policies must be reviewed and narrowed.

{
  "Action": [
    "iam:Get*",
    "iam:List*",
    "access-analyzer:Get*"
  ],
  "Resource": "*"
}
Avoid access keys

Do not build around long-term keys

The enterprise learning path should prefer federated login, temporary role sessions, least-privilege policies, and audit evidence over long-term access keys.

CloudTrail evidence

Future audit trail

CloudTrail would later help show who assumed a role, when, which actions were attempted, and whether any actions were denied.
